# Польова перевірка connectivity-прототипу

Статус: сценарій для першого реального тесту на публічному вузлі й мобільному телефоні.

Цей тест потрібен, бо GitHub Actions уже доводить код, TURN relay у локальному CI, Docker і три ОС, але **не може довести поведінку реальних NAT/CGNAT, мобільної мережі та браузера телефона**.

## 1. Учасники тесту

Потрібні три незалежні точки:

1. **Публічний вузол**
   - VPS/сервер із білою адресою;
   - DNS-ім'я;
   - HTTPS/WSS;
   - gateway;
   - coturn.

2. **Комп'ютер контролю**
   - Windows, macOS або Linux;
   - звичайний інтернет без вимоги білої IP;
   - запущений `cargo-connectivity-control`.

3. **Мобільний пристрій**
   - браузер;
   - спочатку Wi-Fi, потім мобільний інтернет;
   - геолокація дозволена.

Комп'ютер контролю і телефон бажано тримати в різних мережах.

## 2. Сервер

Перед тестом:

- створити тестовий DNS name;
- налаштувати TLS reverse proxy на gateway `127.0.0.1:8080`;
- відкрити TCP 443;
- відкрити UDP/TCP 3478;
- відкрити UDP relay range 49160–49200;
- встановити однаковий `CARGO_TURN_SECRET` у gateway і coturn;
- перевірити `https://<host>/health` → `ok`;
- перевірити стартову сторінку `https://<host>/`.

Не використовувати реальні замовлення або реальні документи.

## 3. Control

Задати:

```text
CARGO_GATEWAY_WS=wss://<host>/signal
CARGO_DRIVER_BASE_URL=https://<host>/
```

Запустити control.

Очікується:
- один стабільний `control_instance_id`;
- два незалежні test trip;
- два готові browser URL;
- після перезапуску control ті самі trip/token відновлюються.

## 4. Тест A — звичайне з'єднання

На телефоні відкрити URL першого рейсу.

PASS:
- стартова сторінка відкрилась по HTTPS;
- token прийнятий;
- WebRTC перейшов у `connected`;
- `control` і `files` channel відкриті;
- control отримав hello;
- браузер отримав synthetic PDF і SHA-256 перевірка успішна.

Зафіксувати selected ICE candidate pair:
- host/srflx → direct;
- relay → TURN.

## 5. Тест B — позиція і статус

На телефоні:
- передати позицію;
- натиснути тестовий статус «прибув».

PASS:
- обидві події мають унікальний event_id;
- control отримав правильний trip_session_id;
- control повернув EventAck;
- браузер прибрав події з локальної черги;
- повторна доставка того самого event_id не створює дубль.

## 6. Тест C — файл browser → control

Вибрати синтетичний PDF або тестове фото.

PASS:
- файл переданий бінарними chunks;
- control звірив size, chunk count і SHA-256;
- повернув FileAck ok=true;
- файл опинився тільки в папці правильного trip.

Не використовувати робочу ТТН чи інший реальний документ у першій пробі.

## 7. Тест D — два рейси одночасно

Відкрити другий trip на іншому браузері/пристрої або окремій browser session.

PASS:
- обидва рейси online;
- status/file рейсу A не з'являється в B;
- розрив A не впливає на B;
- control тримає два незалежні PeerConnection.

## 8. Тест E — примусовий TURN

Для окремої проби заборонити direct-кандидати або використовувати relay-only test mode.

PASS:
- selected pair має `relay`;
- control channel відкривається;
- коротке повідомлення проходить;
- PDF у два боки проходить;
- короткий розрив відновлюється.

Записати обсяг relay traffic для:
- 1 MB;
- 10 MB.

## 9. Тест F — зміна мережі телефона

При активній сесії:

1. телефон на Wi-Fi;
2. вимкнути Wi-Fi;
3. перейти на 4G/5G;
4. повернути Wi-Fi.

PASS:
- браузер не втрачає trip/token;
- після розриву signaling/WebRTC перепідключаються;
- queued status доходить після відновлення;
- event_id не дублюється.

Записати час від розриву до відновленого `connected`.

## 10. Тест G — розрив мережі control

Відключити мережу комп'ютера контролю на короткий час.

PASS:
- control не втрачає локальний state;
- після повернення мережі сам реєструється на gateway;
- браузер отримує новий ICE config;
- WebRTC перебудовується;
- queued event доходить;
- trip ID/token не змінюються.

## 11. Тест H — перезапуск control

Повністю закрити й запустити control.

PASS:
- відновлено той самий control_instance_id;
- відновлені ті самі trip_session_id/token;
- браузер може перепідключитися без нового рейсу;
- старі ACK-підтверджені події не повторюються як нові.

## 12. Тест I — навігатор

З браузерної сторінки перейти в зовнішній навігатор і повернутися.

Перевірити окремо:
- чи лишилась сторінка в пам'яті;
- чи зберігся trip/token;
- чи WebRTC залишився live;
- чи браузер припинив геолокацію у фоні;
- скільки часу займає reconnect після повернення.

PASS не означає «GPS мусить працювати у фоні». Для першої браузерної версії правильна поведінка — **чесно показати, коли позиція перестала надходити**, і відновити її після повернення.

## 13. Тест J — камера і файли телефона

Із браузерної сторінки:
- відкрити камеру;
- зробити тестове фото;
- повернутись;
- передати фото;
- вибрати тестовий PDF через системний file picker.

PASS:
- сторінка рейсу не втрачена;
- обидва файли прив'язані до правильного trip;
- control отримав їх з валідним SHA-256.

## 14. Що записати після тесту

Для кожного сценарію:
- PASS / FAIL;
- телефон/ОС/браузер;
- мережа control;
- мережа телефона;
- direct чи TURN;
- час першого connect;
- час reconnect;
- розмір файла;
- час передачі;
- relay bytes, якщо TURN;
- що сталося після background/foreground;
- короткий текст помилки, якщо FAIL.

## 15. Умова прийняття мережевої схеми

Базову схему можна закрити як придатну, якщо на реальному телефоні та різних мережах:

- control↔browser стабільно встановлюється;
- TURN рятує випадки, де direct не проходить;
- два рейси ізольовані;
- status/position після коротких обривів не губляться й не дублюються;
- PDF/photo проходять у два боки;
- браузер після переходу в навігатор повертається в робочий стан.

Після цього окремо оптимізуються трафік, великі відео та UI — вони не повинні блокувати прийняття базового control-channel.
